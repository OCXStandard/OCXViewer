# OCX Viewer

This application is developed to help find issues in OCX files and to get a better understanding of the OCX format.
It is intended to be used by OCX file authors and consumers to validate and inspect OCX files, not as a generic 3D viewer or editor.

# Architecture

The OCXViewer is implemented as a JAVA rich-client application.

# Build System
The build system is based on Maven. The ``pom.xml`` file contains all dependencies and plugins required to build the application.

## Prerequisites
* A **JDK 25** or higher — the ``pom.xml`` compiles at release 25, so an older JDK will fail. When building from the command line, ensure Maven uses it as the default Java version.
* *Only* for the manual ``java --module-path`` launch shown below: download the JavaFX 21 SDK from https://openjfx.io/ and extract it locally to
    * ``${project.basedir}/binaries/linux/javafx-sdk-21.0.x/lib`` on Linux
    * ``${project.basedir}/binaries/windows/javafx-sdk-21.0.x/lib`` on Windows

  This is **not** required to build, run or package with Maven — ``mvn`` resolves JavaFX from Maven Central.

## Build and run
```
mvn clean install -Dmaven.test.skip=true   # build (test sources are skipped; they do not compile yet)
mvn javafx:run                             # run in development
```

Start the packaged application without Maven, using the following command line arguments on Linux:

```
java --enable-native-access=javafx.graphics 
  --module-path binaries/linux/javafx-sdk-21.0.9/lib:target:target/lib 
  --add-modules javafx.controls,javafx.graphics,javafx.fxml,ocxviewer
  de.cadoculus.ocxviewer.Main --log data/log4j2.xml
```

and on Windows:

```
java --enable-native-access=javafx.graphics 
  --module-path binaries\windows\javafx-sdk-21.0.9\lib;target;target\lib 
  --add-modules javafx.controls,javafx.graphics,javafx.fxml,ocxviewer
  de.cadoculus.ocxviewer.Main --log data\log4j2.xml
```

The differences are only the module-path separator (``:`` on Linux, ``;`` on Windows) and the path separators (``/`` on Linux, ``\`` on Windows). The ``--log`` argument is optional: a default logging configuration is bundled inside the application, so ``--log <file>`` is only needed to point the app at your own ``log4j2.xml``.

## Windows delivery (jpackage)

``mvn package`` produces the Windows delivery under ``target/``. A minimal Java runtime is generated by **jlink** at build time and embedded in the application, so **no JRE is checked into the repository** and end users need no separate Java installation. Two artifacts can be produced:

* **Portable ZIP** — ``target/OCXViewer-<version>.zip``: unzip and run ``OCXViewer/OCXViewer.exe``. Built by default.
* **MSI installer** — ``target/OCXViewer-<version>.msi``: a standard Windows installer (Start-menu entry, in-place upgrades). **Off by default**, because it requires the WiX Toolset (see below).

```
# portable ZIP only (default; no extra tools required)
mvn package -Dmaven.test.skip=true

# ZIP + MSI installer, without editing the pom (also what CI runs)
mvn package -Dmaven.test.skip=true -Dskip-msi=false

# skip native packaging entirely (fast build, produces only the jar)
mvn package -Dmaven.test.skip=true -Dskip-jpackage=true
```

### WiX Toolset (required only for the MSI)

Building the MSI uses ``jpackage``, which on Windows delegates to the **WiX Toolset** to author the installer. WiX is a separate tool: it is **not** provided by Maven or the ``pom.xml``, so it must be installed on every machine that builds the MSI, including any CI node. ``jpackage`` (part of the JDK) auto-detects WiX and supports v3, v4 and v5. This project uses **WiX v4**, installed as a .NET tool:

```
dotnet tool install --global wix --version 4.0.6
wix extension add -g WixToolset.UI.wixext/4.0.6
wix extension add -g WixToolset.Util.wixext/4.0.6
```

Or run the bundled helper, which does the above and verifies the result:

```
tools\install-wix.bat                    (online, from nuget.org)
tools\install-wix.bat C:\path\to\nupkgs  (offline, from a folder of WiX *.nupkg files)
```

* ``wix.exe`` must be on ``PATH`` — the .NET global-tools directory (``%USERPROFILE%\.dotnet\tools``) usually is. WiX 4.0.6 requires a .NET 6 runtime.
* The two extensions are the ones ``jpackage`` passes to ``wix build`` (for the install-directory dialog). They are registered **per user**, so on CI add them as the account the build agent runs as.
* Offline install (e.g. a locked-down CI node): download the WiX ``*.nupkg`` files into a folder, register it as a NuGet source with ``dotnet nuget add source <folder> --name wix-local``, and add ``--add-source <folder>`` to the ``dotnet tool install`` command; the extension commands then resolve from that source too.
* WiX v3/v4/v5 are free for commercial use; avoid v6 and later (maintenance fee).
* The default ``mvn package`` (portable ZIP) needs no WiX at all.

# UI
The UI is implemented in JavaFX. The main components are:
* A menu bar on the top of the window
* A navigation tree on the left side of the window
* A detail view on the right side of the window showing details of the selected element in the navigation tree. In some cases, this detail view allow a drill down to children elements, e.g. follow the panels->panel->stiffener hierachy. 

## Event Handling
Event handling is based on a simple event bus found in the ``de.cadoculus.ocxviewer.event`` package.
This is a copy from the AtlantaFX sample application (https://mkpaz.github.io/atlantafx/).
The following event types are found on the bus
* HotkeyEvent: contains any kind of key events
* OpenEvent: an event fired when a new OCX file is opened
* NavigationEvent: an event fired from the navigation tree
* SelectionEvent: an event fired when an element is selected in the detail view. TODO: merge with NavigationEvent?
* WindowEvent: an event fired when the main window is shown or closed
* ThemeEvent: an event fired when the theme is changed


## Actions
All actions must derive from the ``AbstractAction`` class. The ``de.cadoculus.ocxviewer.actions.ActionDispatcher`` dispatches key events to actions.
This requires the action to contain a static field with the desired key code like 
```
public static final KeyCodeCombination KEYS = new KeyCodeCombination(KeyCode.O, KeyCombination.CONTROL_DOWN);
```
The code to dispatch the action is found in the ``handleHotkeyEvent(HotkeyEvent event)`` method of the ActionDispatcher class.

### About Action
Shows the about dialog containing the building information like version, git commit id and build date.

### Exit Action
Exits the application.
### Help Action
Shows the help dialog.
### Open Action
Opens a file chooser dialog to select an OCX file to open.
### XML Schema Check
Validates an OCX file against the official XSD schema of the selected version (Ctrl+T or the
Actions menu). Runs inside the main window; the file's declared version is auto-detected. See
the bundled schemas under `src/main/resources/xsds/`.
### Schematron
Runs a Schematron rules file (`.sch`) against the raw XML of an OCX file and lists the
violations (F5 or the Actions menu). Runs inside the main window: pick the OCX file (the
currently open one is preselected) and a rules file, then click Validate. No rules file ships
with the application — supply your own `.sch` (the last one you picked is remembered).

Because the OCX namespace is version-specific, a
rules file only matches files of the version it targets; if no rule fires, the viewer says so
rather than reporting a false "valid".

# XML Reading
The data model is automatically generated from the OCX XSD Schema using the hisrc-basicjaxb-tools MVN plugin.
The OCXIO class is the main entry point to read and write OCX files. It enforces all files are read and written using the OCX version 3.1.0 binding.
